# PaperPilot backend handoff prompt

Update only the backend of the existing PaperPilot project at `E:\paper pilot\project`. Preserve the frontend, existing routes, authentication, paper uploads/imports, PDF delivery, conversations, retry processing, notes, and current data. Inspect the current backend before implementing anything. Do not replace existing behavior or change response contracts relied on by the frontend.

The frontend redesign already works with existing endpoints. Upload PDF, arXiv URL import, paper gallery, chat, saved conversations, source-preview navigation, downloads, and Paper View need no new backend button handlers. Paper View opens the fetched PDF in a new tab using the existing authenticated PDF fetch. Takeaway buttons currently ask cited questions through the existing conversation API. References currently shows only genuine cited passages from the active conversation, clearly distinguished from a bibliography.

Implement these additional capabilities if persistent paper-level takeaways and a complete bibliography are desired:

1. Key Takeaways: add authenticated, owner-scoped GET `/papers/{paper_id}/takeaways` and POST `/papers/{paper_id}/takeaways` for retrieving and requesting a cached overview. Include `paper_id`, `status` (`pending`, `processing`, `ready`, `failed`), `updated_at`, and four groups: `central_idea`, `methodology`, `findings`, `conclusions_and_limitations`. Each group contains factual text and explicit source metadata (`section`, positive 1-based `page_start`, optional `page_end`, optional excerpt/chunk identifier). Use only ingested paper evidence. Report insufficient evidence, never invent a summary or citation. Avoid duplicate jobs, cache by paper/content version, and return clear not-ready and retryable-failure responses. Generation should not create unwanted chat messages.

2. References: add authenticated, owner-scoped GET `/papers/{paper_id}/references`. Extract actual bibliography entries from the paper. Return `paper_id`, `status`, and an array of entries with stable `id`, original reference label/text, optional title, authors, year, DOI, validated HTTP(S) URL, and source page/section. Unknown fields stay null. Keep bibliography entries separate from answer evidence passages. Do not fabricate missing DOI, titles, authors, or URLs. Specify whether extraction is complete/partial/unavailable.

3. Evidence metadata: preserve existing conversation answer format and structured `sources`, adding backward-compatible fields only where needed. Stable source identifiers must connect answer labels to actual sections/pages. An answer-source passage and a bibliographic reference are different objects; connect them only when the paper explicitly supports the relationship.

4. Paper metadata: optionally extend existing paper-list responses with verified title/authors/year/arXiv ID, keeping `paper_id`, `filename`, `status`, and existing behavior unchanged. The current UI falls back to the filename. Never infer publication metadata from guesses.

Use existing authentication and ownership checks on every route, including PDF delivery. Do not expose another user's papers through guessed IDs. Do not alter Groq/OpenRouter fallback logic, delete data, run migrations without review, or modify frontend files. Provide tests for ownership, missing/not-ready papers, empty bibliography, missing evidence, duplicate generation requests, and source-page validity. Return the exact API contracts and examples for a separate frontend integration task.

New endpoints are NOT called by the current frontend. After backend completion, a separate frontend change must connect them and render persistent summaries and the full bibliography. Do not claim those integrations already exist. Collections/shared workspaces shown in the design reference are not implemented controls; they are outside this handoff's scope.

## Reference redesign additions
Collections currently persist per account in browser localStorage and require no backend. For cross-device collections, add authenticated collection CRUD and paper-membership routes, with owner checks and backward-compatible frontend integration. Shared with Me currently shows an explicit coming-soon screen: implement invitation/sharing, recipient authorization, revocation, and a shared-paper list before enabling real sharing. The header activity menu uses actual paper-processing status from the existing paper list; it is not a push-notification service. Preserve the working upload, gallery, conversation, retry, PDF, and citation contracts.
